01 / The problem

A failure is visible.
The cause is not.

A single customer checkout can cross multiple services. The first visible error may not be where the problem started.

What customers see

An ordinary purchase suddenly fails. The request passes through connected services, so checkout looks broken—even if the original failure is deeper in the system.

🛒  Customer places an order REQUEST STARTS
Checkout service UPSTREAM
Payment dependency TIMEOUT / ERROR
Checkout response FAILED
Illustrative incident path, not a statement about the current live Astronomy Shop.

What the AI needs to observe

OpenTelemetry connects the investigation to technical evidence instead of having the model invent an explanation.

M
Metrics → How bad?Prometheus: error rates, traffic, latency and resource signals.
T
Traces → Where in the chain?Jaeger: request paths and failing spans.
L
Logs → What exactly happened?OpenSearch: service exceptions and error messages.
H
Health → Is the container unstable?Health signal is simulated in demo; live collector remains a future integration.

Exactly what the LLM can—and cannot—do

01
Choose one next permitted telemetry tool

The model can select among a narrow allowlist based on observed evidence. URLs, targets and arguments are fixed in code.

02
Explain the supported diagnosis

It can produce a concise narrative from verified evidence. It does not get to rewrite the deterministic root cause, confidence or evidence IDs.

03
Fall back safely

On a rate-limit response, the Groq client attempts GPT-OSS 20B. If the call still fails or no key is present, the investigation uses its rule-based path.

04
Never authorise system changes

Actions are chosen from a narrow code allowlist and must pass an independent human gate. No shell access, flag reads or arbitrary URLs are exposed to the model.

“We did not give the language model a production terminal. We gave it bounded observations—and kept execution behind deterministic approval controls.”

07 / Safety by design

A capable agent should
also know when to stop.

Human-in-the-loop isn't merely a prompt instruction; the intended real execution path is constrained by code and persisted approvals.

#
Evidence before actionTwo independent telemetry signal sources, valid ledger citations, and a confidence threshold before proposals.
⌁
Payload-bound approvalSHA-256 of the exact proposed action; changing parameters invalidates the recorded approval.
◉
Fail-closed kill switchExecution blocked by default until explicitly enabled, with a persistent state guard when Redis is configured.
↳
Escalation over guessingHealthy, unknown or unsupported conditions are not converted into invented fixes. No silent automatic rollback.
Scope note: in deployed demo mode, even pressing “approve” simulates a result only. Actual restart/throttle calls remain locked until the organiser's permitted API is connected, approved and tested.
08 / Next integration steps

What remains, and
why we stopped here.

The time-boxed build prioritised an explainable, testable incident workflow and safety boundary. The dependencies below are the path to full live operation.

01
External dependency

Connect the real Astronomy Shop

Bring up the OpenTelemetry Demo with its telemetry backends on an authorised Docker-capable host. Establish secured, reachable endpoints for the investigation API.

Needed for real failures rather than synthetic fixtures.
02
Telemetry validation

Calibrate metrics, traces, logs and health

Map actual Prometheus labels and PromQL, verify the deployed Jaeger API shape, map OpenSearch indices, and add an authorised container-health feed.

Adapters are written; real end-to-end fidelity is not yet established.
03
Organiser integration

Wire the official Action API + faultctl

Obtain the organiser's precise allowed routes, request schemas, authentication and fault-injection commands. Test consent, execution, post-check and safe escalation against genuine failures.

We must not guess the contract or modify Docker directly.
04
Reliability infrastructure

Add the always-on detector and durable state

Run continuous alert polling as a separately authorised worker. Configure Upstash Redis for persistent incident state, approval locks, audit continuity and distributed kill-switch state.

Vercel request handlers are not a persistent monitoring daemon.
05
Evaluation / scoring

Implement the official JSON schema

Validate output against the organiser template. Run every provided fault, healthy-system checks, ambiguous cases, declined approvals, kill-switch tests and recovery verification.

Report exports already exist; official acceptance is not yet measured.
06
Final confidence

Prove behaviour on unseen incidents

Record correct, incorrect and uncertain outcomes, strengthen cross-signal diagnosis, and independently exercise the Action API / rollback rules without hard-coded incident answers.

Hidden-test robustness can only be claimed after empirical validation.

10 / One-minute project explanation

How to describe Incident Zero to a judge

We built Incident Zero, an AI on-call engineering platform that turns an application incident into a traceable decision. Our Next.js command center is deployed on Vercel and currently demonstrates eleven synthetic fault conditions. Under the hood, a rule-driven investigator gathers metrics, traces, logs and health evidence, stores them as E1 to E4, corroborates root-cause hypotheses and escalates uncertainty. Qwen 3.8 27B, hosted through Groq, can select the next authorised read-only tool and explain the findings, but safety-critical diagnosis, action selection and human approval remain enforced in code. We added payload-hash binding, a kill switch, restricted action types and report exports. Given the time constraints, we prioritised the complete demonstration and safety architecture. Next, we will connect the real OpenTelemetry environment, validate the telemetry schemas, integrate the organiser's Action API and faultctl, implement always-on detection, and run official evaluation scenarios.
